# Архитектура

## Слои

```
          ваш код                         ecst-go                      Kafka
┌──────────────────────┐      ┌──────────────────────────┐
│ бизнес-логика        │      │                          │
│  UPDATE orders       │─tx──>│                          │
│  INSERT outbox       │      │                          │
└──────────────────────┘      │                          │
                              │                          │
┌──────────────────────┐      │  ┌────────────────────┐  │     ┌─────────┐
│ OutboxStore          │<─────┼──│ outbox worker      │──┼────>│ topic   │
│  (ваша БД)           │      │  │  producer.Producer │  │     └─────────┘
└──────────────────────┘      │  └────────────────────┘  │
                              │                          │
┌──────────────────────┐      │  ┌────────────────────┐  │     ┌─────────┐
│ Handler[T]           │<─────┼──│ inbox worker       │<─┼─────│ topic   │
│  условный upsert     │      │  │  пул consumer'ов   │  │     └─────────┘
└──────────────────────┘      │  │  DLQ на топик      │──┼────>│ dlq     │
                              │  └────────────────────┘  │     └─────────┘
                              └──────────────────────────┘
```

Пакеты снизу вверх:

- `backoff` — ни от чего не зависит;
- `envelope` — формат события, про Kafka не знает;
- `producer`, `consumer` — транспорт поверх `franz-go`;
- `ecst` — собирает все вместе в `Service`.

Пакеты `producer` и `consumer` используются и самостоятельно, без `ecst` — см. [`example/basic`](../example/basic).

## Почему именно так

**Outbox, а не прямая публикация.** Отправить событие в Kafka и записать изменение в свою БД —
две разные операции, и между ними процесс может упасть. Outbox-таблица сводит их в одну транзакцию:
дальше воркер гарантированно вытащит строку и опубликует, сколько бы раз ни перезапускался сервис.

**По продюсеру на каждую часть.** `Outbox` и `Inbox` поднимают свои `producer.Producer`:
публикация и DLQ требуют разных настроек надежности и не должны делить один буфер. Outbox пишет
потоком и способен занять буфер целиком, а DLQ-запись, которой не хватило места, встает поперек
своей партиции.

**По консьюмеру на топик, а не один на все.** Топики разведены по отдельным консьюмерам, чтоб пул
и его размер настраивались на топик: у разных потоков событий разный объем и разная цена обработки.
Консьюмеры одного топика живут в одной группе и делят между собой его партиции.

**По горутине на партицию.** Цикл поллинга ничего не обрабатывает — он только раздает батчи воркерам
и сразу вызывает `AllowRebalance`. Поэтому долгая обработка одной партиции не задерживает ребаланс
и не блокирует остальные партиции. В пределах партиции порядок строгий.

## Жизненный цикл

```go
svc, err := ecst.New(cfg) // поднимает клиентов, ничего не читает и не пишет
defer svc.Close(ctx)      // гасит консьюмеров, потом флашит продюсеров
svc.Run(ctx)              // блокируется до отмены ctx
```

`Run` не возвращает ошибку: сбой одного батча или одной партиции не должен ронять сервис — такие
случаи уезжают в лог и в DLQ.

`Close` вызывают **после** возврата из `Run`, и порядок в нем важен: сначала консьюмеры (их закрытие
дожидается, пока воркеры доработают и закоммитят текущие батчи), потом продюсеры — через них уходят
DLQ-записи этих самых консьюмеров.

Контекст внутри `Close` отвязан от отмены (`context.WithoutCancel`), но с таймаутом 30 секунд: на
shutdown `ctx` уже отменен, и иначе недоотправленные записи потерялись бы, — а без таймаута сервис
висел бы вечно на недоступном брокере.

### Рендер

Исходники — `.puml` рядом с картинками. Пересобрать после правки:

```bash
cd docs/diagrams
for f in *.puml; do
  docker run --rm -i plantuml/plantuml -tsvg -charset UTF-8 -pipe < "$f" > "${f%.puml}.svg"
done
```

Проверить синтаксис, ничего не перезаписывая:

```bash
docker run --rm -v "$PWD/docs/diagrams:/work:ro" -w /work \
  plantuml/plantuml -checkonly -charset UTF-8 "*.puml"
```
